# 資料來源排障：當行情「看起來缺資料 / 過期」時

## 何時用
選股或回溯發現某日無資料、或日期停在昨日而非今日時，先做这套诊断再下結論。目的：別把「端點落後」誤判成「資料沒了」（錯刪有效報告），也別把「真的未出」當成正常。

## 診斷步驟（依序，別跳）
1. **先確認呼叫沒錯（路徑 / 參數 / HTTP 方法）。**
   - 換文件記載的替代調用再試：GET 不行試 POST（或反之）、補文件要求的參數、查官方 Swagger。
   - 判讀：換法後若「回 200 + 結構正常的資料」→ 路徑對，問題在內容不在呼叫；仍 404/空頁 → 才是路徑/權限錯。
   - ⚠ 回的正常資料「日期不對」時，先走完 2、3 步再動程式——很可能是設計或落後，不是呼叫錯。

2. **區分「文件明訂行為」與「真的過期」。*
   - 有些端點文件寫死「只回最新一期快照」「date 參數被忽略」。這種日期不對是**設計**，不是缺陷；查 Swagger 確認它是否宣稱支援歷史查詢。
   - 若本可回溯卻只給最新 → 才可能是過期或呼叫錯。

3. **找第二個「獨立」來源交叉比對 freshness，再下結論。**
   - 換不同端點/主機查同一天。若 A 無當日、B 有 → 是**端點專屬落後**（各自 batch/update 時程不同），不是資料消失。
   - 分叉：A 真缺、B 有 → 用 B 類來源 fallback；所有獨立來源都無當日 → 才是「資料未出 / 休市」，停跑告知。

## 本環境已知事實（TWSE，2026-10）
- `openapi.twse.com.tw/v1/exchangeReport/STOCK_DAY_ALL`：路徑正確（POST/GET 均回 200）；`?date=` 被忽略是文件明訂的「只回最新一期快照」設計，非 bug。
- 它會單邊落後：當日 STOCK_DAY_ALL 可能停在昨日，但主站 `twse.com.tw/rwd/zh/fund/T86` 已放出當日（兩端點 freshness 不同源）。→ screen_latest 用 Yahoo fallback 是正解。
- `_fetch_json` 已加重試；TWSE 拿不到時 screen_latest 改用 Yahoo 單源而非中止（見 SKILL.md 必記坑「TWSE 過期 fallback」）。

## 常見陷阱
- 把「端點落後」直接當成「選股結果不可靠 / 要刪報告」——其實只是日期比今日少一天，換源即可。
- 沒交叉比對就改程式去「抓歷史」——若端點本就不支援歷史（快照設計），改了也没用。
- 只重試一次就放棄——瞬態 bot-wall/network blip 通常重試即恢復；但重試治標，先確認不是第 2 步的設計行為。
